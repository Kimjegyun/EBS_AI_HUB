## 프로젝트 세부 내용

### 개발 배경 및 목적

```
업무 도구는 회사마다 처음부터 다시 만듭니다. 자산과 비품을 관리하고, 일정을 나누고,
문서를 정리하고, 이제는 AI를 업무에 붙입니다. 하는 일은 거의 같은데 결과물은 각자의
서버 안에 갇혀 밖으로 나오지 않습니다. 그래서 다음 회사도 처음부터 다시 만듭니다.

이 프로젝트는 그 반복을 끊으려고 만들었습니다. 목표는 세 가지입니다.

첫째, 누구나 내려받아 그대로 쓸 수 있어야 합니다.
전체 소스와 문서를 공개했고, 직접 의존성 60개가 모두 MIT·Apache-2.0·BSD 계열이라
카피레프트 제약이 없습니다. 서버 한 대와 브라우저만 있으면 되고 별도 DBMS도
라이선스 비용도 필요하지 않습니다. 개발 인력이 없는 조직도 도입할 수 있게 하려는
것이 기준이었습니다.

둘째, 쓰는 사람이 직접 고쳐 자기 회사에 맞출 수 있어야 합니다.
그래서 앱을 플랫폼에서 분리했습니다. 앱 하나는 파일 하나이고, 셸 코드를 건드리지
않고 추가됩니다. 자산 열 매핑처럼 조직마다 다른 부분은 한 곳에 모았고, 앱마다
실행 순서와 메뉴얼 문서를 두어 처음 보는 사람도 이어받을 수 있게 했습니다.

셋째, 만든 앱을 서로 주고받을 수 있어야 합니다.
앱을 파일 하나로 내보내면 다른 회사의 허브에서 가져오기 한 번으로 설치됩니다.
메타데이터와 코드가 함께 들어 있어 받는 쪽이 따로 입력할 것이 없고, 무결성 확인용
해시가 함께 기록됩니다. 각자 만든 앱이 조직 경계를 넘어 쌓이게 하려는 장치입니다.
빌드 도구도 필요 없어서, 업무를 아는 사람이 직접 만들어 올릴 수 있습니다.

지금은 저희 회사에서 실제로 필요한 앱들을 이 플랫폼 위에서 개발하고 있습니다.
그중 공적으로 쓸 수 있는 기능은 오픈소스로 정리해 계속 공개할 계획입니다.
플랫폼과 앱이 함께 자라는 구조를 만드는 것이 이 프로젝트의 방향입니다.

첫 사례로 만든 것이 자산 실사(재물조사) 앱입니다. 플랫폼이 실제 업무를 감당하는지
검증하려고 가장 번거로운 업무를 골랐습니다. 방송장비 9,291건의 실데이터로 동작하며,
현장에서 QR만 찍으면 자산 조회부터 검수 기록, 기존 양식 그대로의 엑셀 산출,
진척 집계까지 자동으로 흐릅니다. 통신이 끊기는 스튜디오와 기계실을 전제로
오프라인에서도 조사가 이어집니다.
```

### 개발 환경

```
○ 하드웨어
  - 개발/서버: Windows 11 PC (사내망 상시 구동, 로컬 서버 겸용)
  - 현장 단말: Android / iOS 스마트폰 (브라우저 PWA 설치, 별도 앱 배포 불필요)

○ 프론트엔드
  - React 19.2 / TypeScript 6.0 / Vite 8.0
  - Tailwind CSS 3.4 (디자인 토큰 기반 라이트·다크 테마)
  - React Router 7.15 (SPA 라우팅), react-grid-layout 1.4 (대시보드 위젯 배치)
  - html5-qrcode 2.3 (카메라 QR 스캔), qrcode 1.5 (설치 QR 생성)
  - xlsx(SheetJS) 0.18 / exceljs 4.4 (엑셀 읽기·쓰기, 셀 서식)
  - vite-plugin-mkcert 1.17 (로컬 신뢰 HTTPS — 카메라·PWA는 보안 컨텍스트 필수)

○ 백엔드
  - Node.js / Express 4.22 / TypeScript 5.9
  - SQLite (sqlite3 5.1) — 무설치 단일 파일 DB, 사내 서버에 그대로 배치
  - helmet 7.2, cors, express-rate-limit 7.5, jsonwebtoken 9.0, bcrypt 5.1 (보안)
  - multer 2.2 (엑셀 업로드), winston 3.19 (로깅)

○ AI 보조 기능 (선택 사항 — 핵심 기능은 AI 없이 동작)
  - OpenAI 호환 규격으로 요청하며, /responses 실패 시 /chat/completions 로 폴백
  - 따라서 Ollama·llama.cpp·vLLM 등으로 오픈웨이트 모델(Qwen2.5, Gemma, Llama 등)을
    자체 환경에 내려받아 구동하는 경로를 그대로 지원 (설정에서 base URL만 교체)
  - 상용 API 없이도 동일 기능이 작동함 — 실행 방법은 doc/LOCAL_MODEL.md 참고

○ 개발 도구
  - ESLint 10 + typescript-eslint 8 (정적 분석)
  - tsx (서버 핫리로드), ngrok (외부 단말 접속 터널)
  - 코드 작성·디버깅 보조로 Anthropic Claude(Claude Code) 활용

○ 규모
  - TypeScript/TSX 159개 파일, 약 28,400 라인
  - 직접 의존성 60개 — 전부 MIT / Apache-2.0 / BSD 계열 (카피레프트 없음)

### 시스템 구성 및 아키텍처

```
○ 전체 구성
  [현장 폰 PWA] ──HTTPS──┐
                          ├──> [Express API 서버 :3001] ──> [SQLite]
  [사내 PC 브라우저] ─────┘            │                      └ 자산 데이터셋 / 조사 세션
                                       └──> [파일 저장소] 원본 엑셀·산출물

○ 3계층 구조
  1) 앱 허브 셸 — 로그인, 대시보드, 마켓플레이스, 사용자 관리
  2) 앱 플러그인 — registry.ts 한 곳에 등록하면 대시보드·마켓플레이스에 자동 노출
     (캘린더 / 나의 LLM / 메일 생성기 / Codex / 재물조사 / 빠른 작업 / 할 일 /
      메시지 / 메모 / 바로가기 — 10종)
  3) 독립 실행 PWA — 재물조사는 로그인 없이 폰에서 단독 구동 (inventory.html)

○ 원격 앱 로딩 흐름
  ① 관리자가 앱 번들(.js) 업로드 → 서버가 검증 후 보관 + SHA-256 기록
  ② 허브가 로그인 후 등록 목록 조회 → 번들을 인증 요청으로 수신
  ③ Blob URL 로 만들어 동적 import → 팩토리에 호스트 React 주입
  ④ 반환값을 AppPlugin 계약에 맞게 검증 → 런타임 레지스트리에 등록
  ⑤ 마켓플레이스·대시보드·설치 관리 화면에 자동 반영 (재빌드 없음)

○ 핵심 데이터 흐름 (재물조사)
  ① 관리자: 운영관리부 전사 양식(.xlsx) 업로드 → 서버가 시트 목록 파싱 = 본부 목록
  ② 관리자: 본부별 ERP 자산현황(.xlsx) 업로드
     → 서버가 자산번호 기준으로 두 파일을 병합해 본부별 데이터셋 생성
     → ERP 원본은 서버에 보관 (현장 앱이 자동으로 받아 씀)
  ③ 현장: 폰이 데이터셋을 IndexedDB에 캐시 → 이후 오프라인 동작
  ④ 현장: QR 스캔 → 자산번호 추출 → 2단계 매칭(정확 일치 → 하이픈 무시)
     → 자산명·설치장소 자동 표시 → 검수 결과 저장
  ⑤ 오프라인이면 로컬 큐에 적재, 연결 복구 시 자동 동기화
  ⑥ 산출물 2종 생성 → 서버 보관 + 기기 저장
  ⑦ 통계: 데이터셋 전체 자산을 분모로 본부 → 부서 → 확인자 집계

○ AI 보조 계층 (선택)
  - 자산 실사 핵심 경로(스캔·조회·병합·검수·엑셀·통계)는 AI를 호출하지 않음
  - 장부·현물 대조 교차검증 등 보조 기능만 AI 프록시를 경유
  - AI 프록시는 base URL 교체만으로 자체 구동 오픈웨이트 모델로 전환 가능
    (상용 API 미사용 상태에서도 동일 기능 작동을 확인함)

○ 오프라인 설계
  - Service Worker: 앱 셸 캐싱, 네트워크 우선 + 캐시 폴백
  - IndexedDB: 자산 마스터, 조사 세션, 현물 사진, ERP 색인
  - 동기화 큐: 실패한 저장을 재시도, 연결 복구 시 자동 전송
  - 사진은 기기에만 저장 (서버 전송 없음)
```

### 프로젝트 주요 기능

#### 프로젝트 상세 내용 (핵심 기능 및 특장점)

```
[오픈소스로서의 구조 — 이 프로젝트의 핵심]

① 내려받아 그대로 쓰고, 고쳐 쓸 수 있다
   전체 소스와 앱별 실행 문서를 공개했습니다. 직접 의존성 60개가 전부 MIT·Apache-2.0·
   BSD 계열이며 GPL 계열은 0건이라, 재배포·상용 활용·수정에 제약이 없습니다.
   서버 한 대와 브라우저면 동작하고 SQLite 단일 파일 DB라 별도 DBMS가 필요 없습니다.
   조직마다 다른 부분(자산 열 매핑 등)은 한 곳에 모아 두어 고칠 자리를 찾기 쉽습니다.

② 만든 앱을 내보내고 가져올 수 있다 — 조직 사이의 이식
   앱을 파일 하나(.aihubapp.json)로 내보내면, 다른 회사의 허브에서 가져오기 한 번으로
   설치됩니다. 메타데이터와 번들 코드가 함께 들어 있어 받는 쪽이 입력할 것이 없고,
   SHA-256 이 함께 기록되어 파일이 바뀌었는지 확인합니다.
   A조직이 만든 앱을 B조직이 파일만으로 복원해 실행하는 것까지 확인했습니다.

③ 공동 마켓플레이스형 앱 플랫폼
   앱 하나를 파일 하나로 만들고 레지스트리에 한 줄 등록하면 마켓플레이스·대시보드·
   설치 관리 화면에 자동으로 반영됩니다. 셸 코드를 고칠 필요가 없습니다.
   관리자는 조직에 필요한 앱만 게시하고, 사용자는 그중 원하는 것만 설치하며,
   설치 상태는 사용자별로 따로 관리됩니다. 현재 10종이 함께 배포됩니다.

④ 원격 앱 배포 — 재빌드 없이 앱 추가
   앱 번들(정적 import 없는 ESM 한 파일)을 관리자 화면에서 올리면, 허브가 실행 중에
   내려받아 등록합니다. 허브를 다시 빌드하거나 재배포할 필요가 없고, 앱을 만드는
   쪽도 빌드 도구가 필요 없습니다.
   번들은 호스트가 넘겨주는 React 를 받아 앱 정의를 돌려주는 팩토리를 내보냅니다.
   React 를 따로 번들하지 않으므로 인스턴스가 둘로 갈리지 않습니다.
   서버는 업로드 시 ESM 여부·정적 import 없음·크기·앱 id 형식을 검증하고 SHA-256 을
   기록하며, 번들 본문은 인증된 요청으로만 내려갑니다. 앱 하나가 실패해도 나머지는
   정상 등록되고 실패 사유가 관리자 화면에 표시됩니다.

⑤ 앱이 공유하는 AI 계층
   개별 앱이 각자 AI를 연동하지 않고 플랫폼의 AI 프록시를 함께 씁니다.
   OpenAI 호환 규격이라 상용 API와 자체 구동 오픈웨이트 모델을 설정 한 줄로
   바꿔 끼울 수 있습니다.

[플랫폼 위의 앱 사례 — 재물조사]

⑥ 하이픈 무시 자산번호 매칭
   자산 라벨 QR은 QQ000120240000, ERP는 QQ00012-0240-000으로 표기가 다릅니다.
   영숫자만 남긴 보조 키를 색인에 함께 넣어 정확 일치 → 하이픈 무시 순으로 조회합니다.
   기존 조사 결과의 저장 키를 바꾸지 않아 과거 데이터와 호환됩니다.
   구자산번호로도 색인해 라벨에 구번호가 찍힌 자산까지 조회됩니다.

⑦ 오프라인 우선 PWA
   스튜디오·기계실처럼 통신이 끊기는 현장을 전제로 설계했습니다.
   자산 마스터·조사 결과·사진을 IndexedDB에 두고, 네트워크가 없으면 로컬 큐에
   쌓았다가 복구 시 자동 동기화합니다. 앱 스토어 배포 없이 QR 한 번으로 설치됩니다.

⑧ 업무 양식을 그대로 지키는 엑셀 왕복(round-trip)
   담당자가 쓰던 ERP 파일의 열과 서식을 유지한 채 맨 앞에 검수 4열
   (검수완료 / 검수인부서 / 검수인 / 검수날짜)만 끼워 넣어 새 파일을 만듭니다.
   새 양식을 배우게 하지 않고 기존 업무 흐름에 그대로 얹힙니다.

⑨ 설치부서 변경을 색으로 드러내는 대조 파일
   운영관리부 양식의 설치부서를 ERP와 자산별로 대조해, 이전과 같으면 노란색,
   바뀌었으면 주황색으로 셀을 칠하고 원래 부서를 셀 메모로 남깁니다.
   SheetJS 커뮤니티 버전이 셀 채우기를 쓰지 못해 이 산출물만 exceljs로 처리했습니다.

⑩ "다 했는가"를 답하는 커버리지 통계
   조사 건수가 아니라 데이터셋의 전체 자산을 분모로 삼습니다.
   본부 → 설치부서 → 확인자 3계층으로 펼쳐 부서별 진행률과 확인자별 실적을 보여주고,
   미확인 자산은 자산번호·자산명·모델·설치장소까지 표로 제시합니다.
   100% 도달 여부가 화면에서 즉시 확인됩니다.

○ 개발 과정
  1) 실제 재물조사 업무를 관찰해 병목(표기 불일치·오프라인·집계)을 특정
  2) 앱 플랫폼 셸과 플러그인 계약(AppPlugin 인터페이스)을 먼저 확정하고
     마켓플레이스·설치 관리 흐름을 세움
  3) 재물조사 앱을 실데이터(방송장비 9,291건)로 반복 검증하며 개발
  4) 현장 피드백에 따라 수동 단계를 제거 — 소속 자유입력 → 배부 목록 선택,
     ERP 파일 수동 첨부 → 서버 자동 로드
  5) 앱마다 실행 순서·메뉴얼 문서를 두고 코드와 함께 갱신하는 규칙을 적용
```

#### 프로젝트의 혁신성 및 차별성

```
○ 현장 데이터의 "지저분함"을 정면으로 다뤘습니다
  대부분의 자산관리 도구는 자산번호가 깨끗하다고 가정합니다. 이 프로젝트는
  QR과 ERP의 표기가 다른 현실을 전제로 이중 색인을 설계했고, 그 과정에서
  기존 저장 키를 깨뜨리지 않는 방식을 택했습니다.

○ 엑셀을 버리지 않고 감쌌습니다
  업무 전산화가 실패하는 흔한 이유는 담당자에게 새 양식을 강요하기 때문입니다.
  이 프로젝트는 기존 파일의 열과 서식을 보존하고 필요한 열만 앞에 덧붙입니다.
  결과물을 받는 쪽(운영관리부·ERP 담당자)의 업무가 바뀌지 않습니다.

○ 색으로 말하는 산출물
  설치부서 변경 여부를 노랑/주황 셀로 표현하고 원래 값을 메모로 남깁니다.
  보고받는 사람이 스크롤만 해도 무엇이 바뀌었는지 보입니다.

○ 집계의 분모를 바꿨습니다
  "몇 건 조사했다"가 아니라 "전체 중 몇 %"를 보여줍니다. 분모를 데이터셋 전체
  자산으로 잡는 단순한 변경이지만, 관리자가 묻는 질문("다 끝났나?")에 처음으로
  답할 수 있게 됐습니다.

○ 앱이 조직 경계를 넘는다
  사내 플랫폼에서 만든 앱은 보통 그 회사 안에서 끝납니다. 이 프로젝트는 앱을 파일
  하나로 내보내고 가져올 수 있게 해서, A조직이 만든 앱을 B조직이 그대로 설치해 씁니다.
  받는 쪽은 메타데이터를 입력할 필요도, 빌드할 필요도 없습니다.
  업무 소프트웨어를 사고파는 상품이 아니라 서로 주고받는 공동 자산으로 두려는 설계입니다.

○ 재배포 없이 자라는 마켓플레이스
  보통 사내 플랫폼에 앱을 하나 더 넣으려면 코드를 고치고 빌드하고 다시 배포해야 합니다.
  이 프로젝트는 앱 번들을 올리는 것만으로 실행 중에 등록됩니다. 앱을 만드는 쪽도
  빌드 도구가 필요 없어, 업무를 아는 사람이 직접 만들어 올릴 수 있습니다.
  React 인스턴스를 호스트가 주입해 훅이 깨지지 않게 한 것이 이 구조의 핵심입니다.

○ 내부 도구를 공공재로 바꾸는 설계
  사내에서 쓰려고 만든 도구는 보통 그 회사의 사정이 코드 곳곳에 박혀 다른 곳에서
  쓸 수 없습니다. 이 프로젝트는 앱을 파일 하나로 분리하고, 자산 열 매핑을 한 곳에
  모으고, 앱마다 실행 순서 문서를 두어 **처음 보는 사람도 이어받을 수 있는 상태**를
  유지했습니다. 공개를 나중에 붙인 것이 아니라 처음부터 전제로 만들었습니다.
  업무 소프트웨어를 사고파는 상품이 아니라 함께 키우는 공동 자산으로 두자는 시도입니다.

○ 상용 API에 묶이지 않는 AI 계층
  AI 보조 기능을 OpenAI 호환 규격으로 추상화해, 상용 API와 자체 구동 오픈웨이트 모델을
  설정 한 줄로 바꿔 끼울 수 있습니다. 조직 정책상 외부로 데이터를 보낼 수 없는 환경에서도
  로컬 모델로 같은 기능을 쓸 수 있습니다.

○ 문서를 코드와 함께 관리합니다
  앱마다 실행 순서·메뉴얼·데이터 저장 위치·알려진 한계를 담은 문서를 두고,
  기능을 바꿀 때 같은 작업 안에서 갱신하는 규칙을 정했습니다.
  오픈소스로 공개했을 때 다른 사람이 이어받을 수 있는 상태를 유지합니다.

#### 한계점 및 향후 발전 로드맵

```
○ 현재 한계
  - 현장 PWA는 로그인 없이 공유 토큰으로 서버에 접근합니다. 설치 단말이
    늘어나면 기기별 인증이 필요합니다.
  - 데이터셋 삭제에 되돌리기가 없습니다. 실제로 개발 중 9천여 건 데이터셋이
    확인창 한 번으로 삭제된 사고가 있었고, SQLite 미사용 페이지에서 99.6%를
    복구했습니다. 휴지통 테이블과 복원 API가 필요합니다.
  - 커버리지 통계는 요청마다 데이터셋 전체를 파싱합니다. 수십만 건 규모에서는
    캐시가 필요합니다.
  - 외부 접속을 터널에 의존해 주소가 재시작마다 바뀝니다.
  - 부서 집계는 자산의 설치부서 기준이라, ERP에 없는 자산은 부서 미상으로 모입니다.
  - 원격 앱은 샌드박스에서 실행되지 않습니다. 허브와 같은 권한으로 동작하므로
    관리자만 올릴 수 있게 막고 SHA-256 을 기록하지만, 소스를 확인한 앱만 올려야
    합니다. 앱 서명·권한 선언·iframe 격리는 로드맵입니다.

○ 로드맵
  1단계 (단기) — 데이터 안전장치
    삭제 시 휴지통 보관 + 복원 API, 산출물 파일 관리 화면, 자동 백업
  2단계 (중기) — 운영 성숙도
    기기별 등록·인증, 커버리지 통계 캐시, 고정 도메인 배포 가이드,
    조사 이력 감사 로그
  3단계 (장기) — 공개 범위 확대
    자사에서 개발 중인 업무 앱 가운데 공적으로 쓸 수 있는 것을 순차 공개,
    앱 서명·권한 선언·iframe 격리로 외부 앱을 안전하게 받는 구조 마련,
    도메인 확장
    자산 유형별 템플릿(전산장비·도서·실험기자재), 다국어,
    사진 기반 자산 상태 자동 판정, 타 조직이 바로 쓸 수 있는 설치 패키지 배포
```

```
가장 크게 배운 것은 "동작하는 것"과 "현장에서 쓰이는 것"의 거리였습니다.
자산 조회 기능을 만들고 나서도 현장에서는 여전히 조회가 안 되는 자산이 있었고,
원인은 알고리즘이 아니라 QR과 ERP의 하이픈 표기 차이라는 아주 단순한 것이었습니다.
데이터를 직접 열어보기 전까지는 보이지 않는 문제였습니다.

수동 단계를 하나씩 없애는 과정도 기억에 남습니다. 처음에는 소속을 직접 입력하고
ERP 파일도 폰에서 첨부하게 했는데, 관리자가 이미 올린 정보를 현장에서 또 넣게
하고 있다는 지적을 받고 두 단계 모두 자동화했습니다. 기능을 더하는 것보다
불필요한 단계를 빼는 쪽이 더 어려웠습니다.

개발 중 실데이터를 삭제하는 사고를 겪은 것도 값진 경험이었습니다.
SQLite가 삭제 직후에는 페이지를 재사용하지 않는다는 점을 이용해 오버플로 페이지
체인을 되짚어 99.6%를 복구했지만, 애초에 되돌릴 수 있는 설계였다면 필요 없는
작업이었습니다. 파괴적인 동작에는 안전장치를 먼저 두어야 한다는 것을 몸으로 배웠습니다.

오픈소스로 공개하기 위해 문서를 정리하면서, 코드보다 "왜 이렇게 만들었는지"를
남기는 일이 더 중요하다는 것도 알게 됐습니다.
```
