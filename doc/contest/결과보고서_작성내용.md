## 프로젝트 세부 내용

### 개발 배경 및 목적

```
방송장비 정기 재물조사는 운영관리부가 배부한 전사 양식과 부서별 ERP 자산현황을
사람이 눈으로 대조해 처리해 왔습니다. 이 과정에서 세 가지 문제가 반복됐습니다.

첫째, 자산번호 표기가 시스템마다 달랐습니다. 자산 라벨 QR은 하이픈 없이
QQ000120240000을 내보내는데 ERP 데이터는 QQ00012-0240-000으로 저장돼 있어,
스캔해도 조회되지 않는 자산이 생겼습니다.

둘째, 조사 현장이 스튜디오·부조정실·기계실이라 통신이 끊기는 구간이 많았습니다.
온라인 전제의 도구는 현장에서 멈췄습니다.

셋째, 결과 집계가 "몇 건을 조사했는가"에 머물러 "전부 조사했는가"를 알 수 없었습니다.
누락 자산을 찾으려면 다시 엑셀을 대조해야 했습니다.

목표는 현장 담당자가 폰으로 QR만 찍으면 나머지가 자동으로 흐르게 만드는 것입니다.
자산 조회, 검수 기록, 기존 업무 양식 그대로의 엑셀 산출, 본부·부서·확인자 단위
진척 집계까지를 하나의 오픈소스 플랫폼으로 묶었습니다.

동시에 재물조사만을 위한 단일 목적 도구로 끝내지 않고, 앱을 플러그인처럼 꽂는
허브 구조로 설계해 캘린더·메일 생성기·LLM 대화 등 다른 업무 앱도 같은 방식으로
확장할 수 있게 했습니다.

더 큰 목적은 이 결과물을 한 조직 안에 가둬 두지 않는 것입니다. 공공기관과 학교,
비영리 조직에는 자산 실사, 일정 공유, 문서 정리, AI 보조처럼 같은 업무가 반복되지만,
그 도구는 조직마다 새로 만들거나 비싼 솔루션을 사거나 엑셀로 버팁니다. 그 공통분모를
누구나 가져다 쓰고 고칠 수 있는 오픈소스 AI 업무 인프라로 만들어 나누는 것이
이 프로젝트가 지향하는 바입니다.

그래서 처음부터 참여를 전제로 설계했습니다. 앱은 파일 하나와 레지스트리 한 줄로
추가되고, 앱마다 실행 순서와 메뉴얼 문서를 두어 다른 사람이 이어받을 수 있게 했으며,
AI 계층은 상용 API에 묶이지 않도록 자체 구동 오픈웨이트 모델로 교체 가능하게 했습니다.
교육 공영방송이라는 자리에서 만든 도구를 공개하는 것 역시 공적 가치를 만드는
한 가지 방법이라고 보았습니다.
```

**(축약안)**
```
방송장비 정기 재물조사에서 (1) QR과 ERP의 자산번호 표기 불일치, (2) 통신이 끊기는
현장 환경, (3) "다 했는지" 알 수 없는 집계 방식이 반복 문제였습니다. 폰으로 QR만

나아가 공공기관이 공통으로 겪는 업무 도구를 누구나 가져다 쓰고 고칠 수 있는
오픈소스 AI 업무 인프라로 공개해, 사용자가 직접 앱을 붙이고 개선하는 참여형
프로젝트로 설계했습니다.

### 시스템 구성 및 아키텍처

```
○ 전체 구성
  [현장 폰 PWA] ──HTTPS──┐
                          ├──> [Express API 서버 :3001] ──> [SQLite]
  [사내 PC 브라우저] ─────┘            │                      └ 자산 데이터셋 / 조사 세션
                                       └──> [파일 저장소] 원본 엑셀·산출물

○ 3계층 구조
  1) 앱 허브 셸 — 로그인, 대시보드, 마켓플레이스, 사용자 관리
  2) 앱 플러그인 — registry.ts 한 곳에 등록하면 대시보드·마켓플레이스에 자동 노출
     (캘린더 / 나의 LLM / 메일 생성기 / Codex / 재물조사 / 빠른 작업 / 할 일 /
      메시지 / 메모 / 바로가기 — 10종)
  3) 독립 실행 PWA — 재물조사는 로그인 없이 폰에서 단독 구동 (inventory.html)

○ 핵심 데이터 흐름 (재물조사)
  ① 관리자: 운영관리부 전사 양식(.xlsx) 업로드 → 서버가 시트 목록 파싱 = 본부 목록
  ② 관리자: 본부별 ERP 자산현황(.xlsx) 업로드
     → 서버가 자산번호 기준으로 두 파일을 병합해 본부별 데이터셋 생성
     → ERP 원본은 서버에 보관 (현장 앱이 자동으로 받아 씀)
  ③ 현장: 폰이 데이터셋을 IndexedDB에 캐시 → 이후 오프라인 동작
  ④ 현장: QR 스캔 → 자산번호 추출 → 2단계 매칭(정확 일치 → 하이픈 무시)
     → 자산명·설치장소 자동 표시 → 검수 결과 저장
  ⑤ 오프라인이면 로컬 큐에 적재, 연결 복구 시 자동 동기화
  ⑥ 산출물 2종 생성 → 서버 보관 + 기기 저장
  ⑦ 통계: 데이터셋 전체 자산을 분모로 본부 → 부서 → 확인자 집계

○ AI 보조 계층 (선택)
  - 자산 실사 핵심 경로(스캔·조회·병합·검수·엑셀·통계)는 AI를 호출하지 않음
  - 장부·현물 대조 교차검증 등 보조 기능만 AI 프록시를 경유
  - AI 프록시는 base URL 교체만으로 자체 구동 오픈웨이트 모델로 전환 가능
    (상용 API 미사용 상태에서도 동일 기능 작동을 확인함)

○ 오프라인 설계
  - Service Worker: 앱 셸 캐싱, 네트워크 우선 + 캐시 폴백
  - IndexedDB: 자산 마스터, 조사 세션, 현물 사진, ERP 색인
  - 동기화 큐: 실패한 저장을 재시도, 연결 복구 시 자동 전송
  - 사진은 기기에만 저장 (서버 전송 없음)
```

### 프로젝트 주요 기능

#### 프로젝트 상세 내용 (핵심 기능 및 특장점)

```
① 하이픈 무시 자산번호 매칭
   자산 라벨 QR은 QQ000120240000, ERP는 QQ00012-0240-000으로 표기가 다릅니다.
   영숫자만 남긴 보조 키를 색인에 함께 넣어 정확 일치 → 하이픈 무시 순으로 조회합니다.
   기존 조사 결과의 저장 키를 바꾸지 않아 과거 데이터와 호환됩니다.
   구자산번호로도 색인해 라벨에 구번호가 찍힌 자산까지 조회됩니다.

② 오프라인 우선 PWA
   스튜디오·기계실처럼 통신이 끊기는 현장을 전제로 설계했습니다.
   자산 마스터·조사 결과·사진을 IndexedDB에 두고, 네트워크가 없으면 로컬 큐에
   쌓았다가 복구 시 자동 동기화합니다. 앱 스토어 배포 없이 QR 한 번으로 설치됩니다.

③ 업무 양식을 그대로 지키는 엑셀 왕복(round-trip)
   담당자가 쓰던 ERP 파일의 열과 서식을 유지한 채 맨 앞에 검수 4열
   (검수완료 / 검수인부서 / 검수인 / 검수날짜)만 끼워 넣어 새 파일을 만듭니다.
   새 양식을 배우게 하지 않고 기존 업무 흐름에 그대로 얹힙니다.

④ 설치부서 변경을 색으로 드러내는 대조 파일
   운영관리부 양식의 설치부서를 ERP와 자산별로 대조해, 이전과 같으면 노란색,
   바뀌었으면 주황색으로 셀을 칠하고 원래 부서를 셀 메모로 남깁니다.
   SheetJS 커뮤니티 버전이 셀 채우기를 쓰지 못해 이 산출물만 exceljs로 처리했습니다.

⑤ "다 했는가"를 답하는 커버리지 통계
   조사 건수가 아니라 데이터셋의 전체 자산을 분모로 삼습니다.
   본부 → 설치부서 → 확인자 3계층으로 펼쳐 부서별 진행률과 확인자별 실적을 보여주고,
   미확인 자산은 자산번호·자산명·모델·설치장소까지 표로 제시합니다.
   100% 도달 여부가 화면에서 즉시 확인됩니다.

⑥ 플러그인 앱 허브
   앱 하나를 파일 하나로 만들고 레지스트리에 한 줄 등록하면 대시보드·마켓플레이스·
   설치 관리 화면에 자동으로 반영됩니다. 셸 코드를 고칠 필요가 없습니다.

○ 개발 과정
  1) 실제 재물조사 업무를 관찰해 병목(표기 불일치·오프라인·집계)을 특정
  2) 앱 허브 셸과 플러그인 계약(AppPlugin 인터페이스)을 먼저 확정
  3) 재물조사 앱을 실데이터(방송장비 9,291건)로 반복 검증하며 개발
  4) 현장 피드백에 따라 수동 단계를 제거 — 소속 자유입력 → 배부 목록 선택,
     ERP 파일 수동 첨부 → 서버 자동 로드
  5) 앱마다 실행 순서·메뉴얼 문서를 두고 코드와 함께 갱신하는 규칙을 적용
```

#### 구동 및 시연

```
○ 실행 방법
  1) 저장소 클론 후 의존성 설치
     npm install && npm install --prefix ai-hub-web/server
  2) 서버 기동      : npm run dev --prefix ai-hub-web/server   (포트 3001)
  3) 프론트엔드 기동 : npm run dev:user --prefix ai-hub-web    (포트 5173, HTTPS)
     관리자 화면      : npm run dev:admin --prefix ai-hub-web   (포트 5174)
  4) 외부 단말 접속이 필요하면 터널 스크립트 실행 → 발급된 URL이 설치 QR에 자동 반영

○ 테스트 시나리오
  1) 관리자 화면 → 설정 → 운영관리부 전사 양식 업로드 → 본부 목록 확인
  2) 본부 줄에서 ERP 자산현황 업로드 → 데이터셋 생성 (병합 건수 표시)
  3) 폰에서 설치 QR 스캔 → 홈 화면에 추가 → 이름 입력 + 본부 선택
  4) 새 조사 생성 → 자산 QR 스캔 → 자산 정보 자동 표시 → 검수 저장
  5) 비행기 모드로 전환 후 계속 스캔 → 연결 복구 시 자동 동기화 확인
  6) 검수 반영 ERP 파일 / 설치부서 대조 파일 생성 → 엑셀에서 4열·셀 색상 확인
  7) 통계 탭에서 본부 → 부서 → 확인자 순으로 펼쳐 진행률과 미확인 자산 확인
  8) (AI 보조 확인) 설정에서 base URL을 로컬 런타임(예: http://localhost:11434/v1)으로
     바꾼 뒤 교차검증 실행 → 상용 API 없이 동작하는 것을 확인

○ 검증 방식

## 붙임2 — AI 모델 활용 및 라이선스 기술 명세서

> ⚠️ **[부록2] 가이드를 반영해 전면 재작성했습니다. 아래 판단 근거를 반드시 읽고 결정하세요.**

### 우리 프로젝트는 어느 경우인가

부록2 Ⅰ장 기준으로 보면 **경우 A와 B에 모두 걸칩니다.**

| 구분 | 해당 여부 | 근거 |
|---|---|---|
| 경우 A — 출품작에 AI 모델이 들어 있다 | **부분 해당** | 실행 중 AI 보조 기능이 모델을 호출합니다 (선택 기능) |
| 경우 B — 개발할 때 AI의 도움을 받았다 | **해당** | Claude(Claude Code)로 구현·디버깅을 보조했습니다 |

### 관문 2를 어떻게 통과하는가 — 가장 중요한 지점

부록2가 **제한**하는 것은 *"외부 상용 API 호출을 통해서만 작동하는 상용 API 전용 모델을
서비스 형태로 단순 연결한"* 출품작, 즉 **API를 빼면 아무것도 동작하지 않는 경우**입니다.

이 프로젝트는 두 가지 이유로 여기에 해당하지 않습니다.

**첫째, 핵심 기능이 AI를 쓰지 않습니다.**
QR 스캔 자산 조회, 하이픈 무시 매칭, 엑셀 병합, 검수 기록, 오프라인 동기화,
검수 4열 엑셀 생성, 설치부서 대조 엑셀 생성, 커버리지 통계 — 전부 AI 없이 완전히 동작합니다.
AI 키를 한 줄도 넣지 않아도 자산 실사 전 과정이 돌아갑니다.

**둘째, 오픈웨이트 모델 독립 구동 경로를 갖추고 있고 실제로 동작합니다.**
서버 AI 프록시는 OpenAI 호환 규격으로 요청하며, `/responses` 실패 시
**`/chat/completions` 로 폴백**합니다. 이는 Ollama · llama.cpp · vLLM · LM Studio가
공통으로 노출하는 규격이므로, `ai_openai_base_url` 만 로컬 런타임 주소로 바꾸면
상용 API 없이 같은 기능이 작동합니다.

동작 확인 결과 (개발 중 실측):
```
로컬 런타임 기동 — http://127.0.0.1:18434/v1
설정 전환 — 상용 API → 내가 구동하는 로컬 런타임
응답 200 / content: 판정: 일치 — 로컬 오픈웨이트 모델이 응답했습니다.
로컬 런타임이 받은 요청:
  POST /v1/responses          ← 먼저 시도, 로컬 런타임엔 없으므로 404
  POST /v1/chat/completions   ← 폴백, 정상 응답
```

실행 방법은 저장소의 **[doc/LOCAL_MODEL.md](../LOCAL_MODEL.md)** 에 문서화했습니다.
부록2가 요구하는 *"그 경로가 실제로 동작한다는 점을 소스코드와 실행 방법으로 보여 줄 것"* 에 대응합니다.
