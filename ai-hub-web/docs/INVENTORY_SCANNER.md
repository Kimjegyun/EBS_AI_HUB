# 재물조사 카메라 스캐너

`src/apps/inventory/QrScanner.tsx`는 html5-qrcode로 자산번호 라벨의 QR 코드와 1차원 바코드(Code 128/39/93, Codabar, ITF, EAN/UPC)를 읽습니다. Data Matrix도 읽습니다.

## 인식 엔진

스캐너는 두 가지 인식기를 동시에 돌리고, 먼저 읽힌 결과를 씁니다.

1. **원본 해상도 인식기(1차원 바코드용):** `barcodeFrameDecoder.ts`가 카메라 영상을 원본 해상도(예: 1920×1080) 그대로 잘라 `barcodeWorker.ts`(Web Worker, zxing-cpp WASM)로 보냅니다. 모든 기기에서 같은 방식으로 동작합니다.
2. **html5-qrcode:** 카메라 제어와 QR 인식을 맡습니다.

html5-qrcode는 화면에 보이는 미리보기 크기(휴대폰에서 약 360px)로 줄인 이미지를 판독합니다. QR은 칸이 커서 줄여도 읽히지만, 1차원 바코드는 가는 막대가 뭉개져서 읽히지 않았습니다. 그래서 원본 해상도 인식기를 추가했습니다. 가짜 카메라로 넣은 같은 1920×1080 영상(Code 128)에서 html5-qrcode는 20초 동안 읽지 못했고, 원본 해상도 인식기는 읽었습니다.

- 인식 범위는 화면의 가로 띠 영역(16:9)이고, 120ms마다 한 장씩 판독합니다. 이전 판독이 끝나지 않았으면 다음 장을 건너뜁니다.
- 형식: Code 128/39/93, Codabar, ITF, EAN/UPC, QR, Data Matrix. 라벨이 옆으로 누웠거나 뒤집혀 있어도 읽습니다(`tryRotate`).
- Worker를 쓸 수 없는 환경에서는 html5-qrcode만으로 동작합니다.

html5-qrcode 쪽 인식기:

| 환경 | 사용하는 엔진 |
|---|---|
| 안드로이드 Chrome 등 내장 `BarcodeDetector`가 있는 브라우저 | 브라우저 내장 인식기 |
| 아이폰 Safari, Windows/Linux Chrome 등 내장 인식기가 없는 브라우저 | `barcode-detector` 폴리필(zxing-cpp WebAssembly) |

html5-qrcode에 내장된 ZXing-js는 1차원 바코드를 거의 읽지 못합니다. 그래서 `src/apps/inventory/barcodePolyfill.ts`가 내장 인식기가 없는 브라우저에만 폴리필을 설치합니다.

- 이 모듈은 `new Html5Qrcode` 전에 불러와야 합니다. html5-qrcode가 생성 시점에 한 번만 `BarcodeDetector`를 확인하기 때문입니다.
- WASM 파일(`zxing_reader-*.wasm`, 약 1MB)은 CDN이 아니라 앱 빌드 결과물에 포함되어 같은 서버에서 제공됩니다. 처음 스캔할 때 한 번 내려받습니다.

## 번호만 있는 라벨 (글자 인식, OCR)

QR·바코드 없이 자산번호만 인쇄된 라벨(예: `QM00044-0206-000`)은 글자를 읽습니다(`assetOcr.ts`, Tesseract).

- **카메라:** 스캔 화면의 **코드 없는 라벨 · 번호 글자 읽기** 버튼을 누르면 지금 화면을 원본 해상도로 읽습니다. 찾으면 일반 스캔과 똑같이 처리합니다(결과 표시, 저장, 중복 확인).
- **사진 분석:** QR·바코드가 없는 사진은 자동으로 글자 인식을 합니다. 결과에는 **글자 인식** 표시가 붙습니다.
- **오인식 대비:** 글자 인식은 틀릴 수 있어서, **마스터에 있는 자산과 일치할 때만** 인정합니다.
  - 번호 전체가 일치하면 그 자산입니다.
  - 아니면 앞 두 마디(예: `QM00044-0206`)로 자산이 하나로 정해질 때만 인정하고, 끝 마디는 가장 비슷한 번호를 고릅니다. 비슷한 정도가 같으면 `000`을 고릅니다.
  - O↔0, I↔1, S↔5, Z↔2, B↔8 같은 혼동 문자는 숫자로 바꿔 읽습니다. 하이픈 없는 구형 인쇄(`QV000230282000`)도 읽습니다.
- **처리:** 회색조와 대비 보정을 한 뒤 읽습니다. 글자가 작으면 확대하고, 0°에서 못 찾으면 90°/270°/180°로 돌려 다시 읽습니다.
- **엔진 파일 자체 호스팅:** 엔진과 Worker는 Vite 번들에 들어 있습니다. 영어 모델 `eng.traineddata.gz`(2.9MB)는 `vite.config.ts`의 `ocr-model` 플러그인이 `node_modules`에서 `{BASE_URL}tesseract/`로 내보냅니다. 처음 쓸 때 한 번 내려받습니다.
- **첨부 사진 크기:** 첨부 사진은 긴 변 **2048px**로 저장합니다(`photoService.ts`, 기존 1280px). 1280px에서는 세로 사진의 번호 글자가 너무 작아 읽히지 않았습니다.
- **검증:** 현장 사진 9장을 첨부 경로 그대로 글자 인식했습니다.
  - 번호만 있는 라벨(`QM00044-0206-000`)을 포함해 3장을 인식했습니다.
  - 나머지 6장은 바코드·QR이 있어 바코드 판독으로 처리됩니다. 글자 인식은 코드를 찾지 못한 사진에만 쓰입니다.

## 라벨 방향 (세로·거꾸로·거울상)

- **카메라:** 프레임마다 읽는 범위를 번갈아 바꿉니다(`barcodeFrameDecoder.ts`).
  1. 화면 가운데 가로 띠를 원본 해상도로 읽습니다(작거나 먼 바코드용).
  2. 화면 전체를 긴 변 1280px로 줄여 읽습니다(세로로 놓이거나 뒤집힌 라벨용).
  - 예전에는 가운데 띠만 읽어서, 세로 라벨이나 옆으로 놓인 바코드는 띠 밖으로 잘려 실패했습니다.
  - 줄인 화면 전체는 띠와 비슷하게 프레임당 6~9ms라 판독 속도가 그대로입니다.
  - 시험: 세로 라벨 QR(정방향·180°)과 90° 바코드를 실제 판독 경로에 영상으로 넣었더니 모두 약 0.2초 안에 읽었습니다. 기존 방식은 모두 실패했습니다.
- **QR·바코드 자체:** 회전(90/180°), 거울상, 상하 반전 모두 판독됩니다. 현장 사진으로 시험했고 각 30ms 안팎입니다.
- **번호 글자(OCR):** 정방향 → **180°** → 90°/270° → 거울상 순서로 시도하고, 찾으면 바로 멈춥니다.
  - 뒤집힌 라벨은 두 번째 시도에서 읽힙니다. 시험에서 0.41초였습니다.
  - 거울상은 다른 방향이 모두 실패했을 때만 시도해서 평소 속도에는 영향이 없습니다. 시험에서 1.0초였습니다.
  - 첫 두 글자를 비슷한 글자로 잘못 읽는 경우(G↔Q, O↔Q, C↔G 등)도, 읽은 그대로는 마스터에 없을 때만 대체 글자로 다시 찾습니다.

## 비스듬한 촬영 (기울어진 바코드)

- **QR:** 기울어짐(원근), 비스듬한 회전(15~45°) 모두 판독됩니다. 현장 사진 시험에서 0.06초였습니다.
- **1차원 바코드:** 판독기는 막대가 가로·세로 축에서 약 **2°** 안에 있을 때만 읽습니다. 그래서 휴대폰을 비스듬히 대면 15°만 기울어져도 읽지 못했습니다(원근으로 짧아지는 것은 대부분 괜찮습니다).
- **개선 내용(`barcodeWorker.ts`, `readDeskewed`):** 일반 판독이 실패했을 때만 막대 기울기를 재고 곧게 펴서 다시 읽습니다.
  - 기울기 측정: 블록 평균으로 약 640px로 줄여 매끄럽게 한 뒤, Sobel 경계 방향을 90° 단위로 접은 히스토그램의 최댓값을 씁니다. 1920×1080에서 15~25ms 걸립니다.
  - 측정값이 실제보다 약 2° 작게 나와서 측정값+2°, 측정값, 측정값+4° 순서로 시도합니다.
  - 아무것도 못 읽는 동안에는 3프레임에 한 번만 실행해서, 겨누는 동안의 프레임 속도가 거의 그대로입니다. 바로 읽히는 바코드는 이 단계를 거치지 않습니다.
- **시험(실제 카메라 판독 경로, 1920×1080 영상):**
  - 기울어진 바코드(10/20/−25/35°) 12건 중 **10건**을 0.5초 안팎에 읽었습니다. 개선 전에는 0건이었습니다.
  - 정면 바코드는 0.07초로 변화가 없고, QR도 영향이 없습니다.
  - 막대가 아주 촘촘한 라벨 하나는 20°와 35°에서 여전히 읽지 못했습니다. 기울기 측정은 맞았지만 펴는 과정에서 생기는 흐림을 견디지 못하는 것으로 보입니다.
- **현장 팁:** 바코드는 휴대폰을 라벨과 나란히(가로 방향으로) 대면 바로 읽힙니다. 기울여 찍으면 0.5초쯤 더 걸립니다.

## 조명 대응

- **카메라 판독:** 프레임마다 처리 방식을 돌아가며 씁니다(`barcodeWorker.ts`).
  1. 기본(국소 평균 이진화)
  2. **플랫필드 보정:** 주변 밝기로 나눠 한쪽에서 비치는 조명의 밝기 차를 없앱니다.
  3. 반전 + ½ 축소(반사가 있는 라벨, 흐린 초점)
- **사진 분석:** 판독에 실패하면 플랫필드 보정본으로 한 번 더 읽습니다.
- **검증:** 현장 바코드 사진 3장에 조명을 인위적으로 망가뜨려 시험했습니다.
  - 측면 조명(왼쪽 15% → 오른쪽 100% 밝기)에서 기존 방식은 모두 실패했고, 플랫필드 보정은 3장 모두 판독했습니다.
  - 어두움(30%)과 국소 반사광은 기존에도 판독됐습니다.
- **현장 팁:**
  - 반사가 바코드 막대를 가로지르면 어떤 처리로도 복구되지 않습니다. 휴대폰 각도를 조금 바꾸세요.
  - 어두운 곳에서는 스캔 화면의 플래시 버튼을 쓰세요.

## 자동초점

- **연속 자동초점은 시작할 때 한 번만 켭니다** (`cameraFocus.ts`). 이후에는 카메라가 거리를 스스로 따라갑니다.
  - 예전에는 3.5초마다 초점 모드와 노출·화이트밸런스 설정을 다시 보냈습니다. 많은 안드로이드 기기는 이때 초점을 처음부터 다시 잡아서, 라벨을 읽으려는 순간 화면이 흐려졌습니다.
  - 다시 초점을 잡는 경우는 사용자가 화면을 누를 때, 줌을 바꿀 때, 앱으로 돌아올 때뿐입니다.
- **안드로이드 렌즈 선택** (`cameraPick.ts`). 후면 렌즈가 여러 개(기본·광각·매크로·심도)인 휴대폰은 자동초점이 없는 렌즈가 열리기도 합니다. 그런 렌즈로는 가까운 라벨이 절대 선명해지지 않습니다.
  - 처음 스캔할 때 열린 렌즈가 연속 자동초점을 지원하는지 확인합니다.
  - 지원하지 않으면 다른 후면 렌즈를 잠깐씩 열어 보고, 지원하는 렌즈로 바꿉니다. 카메라가 한 번 다시 켜집니다.
  - 고른 렌즈는 그 휴대폰에 기억합니다(`localStorage`의 `inventory-camera-device`). 다음부터는 바로 그 렌즈로 열립니다.
  - 기억한 렌즈가 사라지면(카메라 권한 초기화 등) 기억을 지우고 다시 고릅니다.
  - iPhone은 시스템이 렌즈를 자동으로 바꾸므로 이 과정이 없습니다.
- **현장 팁:** 라벨에 10cm보다 가까이 대면 대부분의 휴대폰은 초점을 맞추지 못합니다. 15~25cm 거리에서 줌(기본 2배)으로 키워서 찍으세요.

## 구형 자산번호 라벨

구형 라벨의 바코드(예: `QM430056000`)도 읽어서 현재 자산으로 등록합니다.

- 구형 번호와 신형 번호는 일련번호가 달라 계산으로 바꿀 수 없습니다(예: 구형 `QM43-0056-000` → 신형 `QM00043-1755-000`). 그래서 마스터 엑셀의 구형 자산번호 열로 찾습니다(`datasetService.buildIndex`).
- 저장되는 번호는 항상 **신형 번호**입니다. 그래서 통계, 본부·전사 엑셀, 중복 확인에서 같은 자산으로 처리됩니다.
- 스캔 결과에는 `QM00043-1755-000 (구형 라벨 QM430056000)`처럼 두 번호가 함께 나옵니다. 사진 분석 목록도 같습니다.
- 마스터에 구형 번호가 비어 있는 자산은 구형 라벨로 찾을 수 없습니다. 이 경우 마스터 엑셀에 구형 번호를 채워 다시 등록해야 합니다. 2026년 마스터 기준으로 본부마다 자산의 41~85%에 구형 번호가 있습니다.

## 스캔 결과 표시

QR·바코드를 읽을 때마다 카메라 화면 바로 아래에 결과가 표시됩니다(`scanFeedback.tsx`).

| 표시 | 조건 |
|---|---|
| ✅ 인식완료 | 이 본부 마스터에 있고, 설치부서가 조사부서와 같음 |
| ⚠️ 타부서자산 | 마스터에 있지만 설치부서가 조사부서와 다름(설치부서도 함께 표시), 또는 이 본부 마스터에는 없고 ERP에만 있는 다른 본부 자산 |
| ❌ 인식실패 | 자산번호 형식이 아니거나 어디에서도 조회되지 않음 |
| ℹ️ 이미 조사됨 | 이미 확인된 자산 |

- 결과는 4초 동안 표시됩니다.
- 스캐너는 판독할 때마다 다시 열리므로, 결과는 조사 화면(`InventoryApp`)이 보관해 다시 열린 스캐너에 넘겨줍니다.
- 연속 스캔에서는 저장 후 다시 열린 카메라 아래에 결과가 보입니다.
- 한 건씩 스캔할 때는 0.8초 동안 결과를 보여준 뒤 입력 화면으로 넘어갑니다.
- 타부서자산도 저장과 입력은 평소대로 됩니다. 표시는 확인용이며, 부서별 교차검증은 통계 화면에서 합니다.

## 사진 분석 (첨부한 라벨 사진)

조사 화면의 **사진 분석** 버튼(스캔·연속 버튼 옆)을 누르면, 조사 화면의 사진 첨부 영역에 올린 사진들에서 QR·바코드를 읽습니다. 첨부한 사진이 없으면 **'분석할 이미지를 첨부하세요.'** 라고 안내합니다.

1. `PhotoBarcodeImport.tsx`가 첨부 사진(입력 중인 자산이 있으면 그 자산의 사진, 없으면 대기 중인 첨부 사진)을 기기 저장소에서 꺼냅니다. 그다음 `decodePhotoFiles`(`barcodeFrameDecoder.ts`)로 같은 Worker에 한 장씩 보냅니다.
   - 첨부 사진은 긴 변 1280px JPEG로 저장되지만, 현장 사진 7장으로 시험했을 때 이 크기에서도 모두 판독됐습니다.
   - 대기 중인 첨부 사진을 분석해 반영하면, 그 사진들은 정리됩니다. 그렇지 않으면 다음에 저장하는 자산에 잘못 붙기 때문입니다.
2. 사진마다 두 번 판독해 결과를 합칩니다. 한 번은 원본 그대로, 한 번은 ½로 줄여서 읽습니다(`downscaleFactor: 2`). 반사가 있거나 기울어진 바코드는 줄였을 때 읽히는 경우가 있습니다.
3. 결과 목록을 보여준 뒤 **N건 조사에 반영**을 누르면 신규 자산만 저장합니다. 상태는 정상, 확인 완료로 연속 스캔 자동 저장과 같고, 설치부서는 마스터 값을 씁니다.

| 표시 | 의미 |
|---|---|
| 신규 반영 | 이 본부 마스터에 있고 아직 조사되지 않음. 반영 대상 |
| 이미 조사됨 | 이 부서 조사에서 이미 확인됨. 건너뜀 |
| 이 본부 자산 아님 | 현재 조사 본부의 마스터에 없음. 건너뜀 |
| 자산번호 아님 | 읽은 값이 자산번호 형식이 아님 |

- 구형 번호 라벨(예: `QX160073000`)도 마스터의 신형 번호(`QV00023-0244-000`)로 찾습니다. 한 기기의 구형·신형 라벨이 둘 다 읽히면 1건으로 합칩니다.
- 반영한 결과는 기기에 저장됩니다. 서버에는 평소처럼 **최종 등록**을 눌러야 올라갑니다.
- 검증: 현장 사진 7장(QR 3장, Code 39 바코드 4장, 4000×3000)을 Chrome의 Worker로 판독해 7장 모두 자산번호를 읽었습니다(약 4초). 그중 광택 있는 검은 기기 사진은 위쪽 라벨에 빛 반사가 지나가 읽지 못했고, 아래쪽 구형 번호 라벨을 ½ 축소 판독으로 읽었습니다.

## 서버 조건

- WASM은 `application/wasm` 형식으로 제공해야 합니다. Express static이 자동으로 이 형식을 붙입니다.
- CSP를 쓰는 서버는 `script-src`에 `'wasm-unsafe-eval'`이 있어야 합니다. `server/src/index.ts`의 helmet 설정에 포함되어 있습니다.

## 배포 반영

코드를 바꾼 뒤에는 외부 공개용 빌드를 다시 만듭니다.

```
node scripts/build-inventory-public.mjs
node scripts/build-public-portals.mjs
```

아이폰에서는 열려 있는 탭이나 홈 화면 앱을 완전히 닫았다가 다시 열어야 새 버전이 적용됩니다.
